# DSH项目整体评估与桌面AI工具对比

**评估日期：2026-10-01｜对象：D:\dsp｜结论：有实际工程基础的个人智能体工作台，建议先补执行可靠性，再扩展功能。**

> 这不是商业产品性能排行榜。本报告区分：现场确认、隔离复现、源码判断、官网介绍和建议。未购买订阅、未调用商业模型跑横评、未启动或关闭桌面产品，未读取聊天记录、真实凭证或当前宿主会话账本。没有修改应用代码、配置、原Git索引或子模块工作树。

## 一、先说结论

**这个项目值得继续，但下一阶段不应以“再装几个插件、再加一层世界观”为主。最值得做的是：让它只做获准的事、失败能解释、改动能核对、恢复能真正成功。**

通俗地分成三部分：

1. **大模型**：负责理解和生成，主要来自外部模型/服务，不是本项目训练出的新模型。
2. **执行层**：把模型意图变成读文件、改文件、跑命令、提交代码等真实动作。这一层已经有基础，但本轮发现了实际边界缺陷。
3. **工作台**：任务、插件、状态、回退、设置、可视化。这里已有较多实现，但还需收敛普通用户的入口和术语。

我的定位判断：**不是空壳，也还不是可以放心交给陌生用户全盘授权的成熟成品；更接近可定制、可审计的个人实验/进阶工作台。** 此判断基于下面的代码和测试证据，不是基于外观或版本号。

### 现在已有的资产

- Open World v2.78.0：系统状态/动作/事件、任务和回退入口、Space角色与路由权限、令牌和短时SSE票据。
- dsh-self：插件能力归属、宿主命令入口、路径限制、预览、执行记录、步数预算。
- Rewind桥接：写文件前保存快照，快照失败时拒写，已有H1–H5检查。
- 组合客户端有生成一致性检查，当前`check:client`通过，不能把它描述成“完全没构建门禁”。
- 项目自己明确把RRA标为`implemented:false / fullNeuralRra:false`，这份诚实边界应保留。

### 现在最缺的不是模型名单

- 可证明的权限边界，而不只是参数中出现`confirm:true`。
- 任务级隔离、精确变更范围与可靠恢复。
- 在真实桌面/升级/断网/取消等情况下的端到端验证。
- 一份可信的运行时与插件事实清单，而不是多份逐渐漂移的说明。

## 三、优先修复的4个已复现问题

优先级定义：**P0＝在扩大自动执行或交付前解决；P1＝本轮核心可靠性修复；P2＝随后治理和体验优化。** 这不是“已经被人利用”或“数据已经泄露”的判断。

### F01｜P0：命令参数可以绕过工作目录限制

**现场隔离复现：** 临时仓库直接用路径接口检查会被拒绝，但通过Git自身的切换目录参数执行只读查询，仍能访问该仓库。本轮只查询虚构仓库位置，没有读写白名单外的真实文件。

**原因：** `shellRun`检查cwd及该cwd对应的Git根，但随后原样传递Git参数；Git自身的全局选项可改变实际操作对象。禁止shell元字符或设置`shell:false`并不等于操作系统沙箱。类似地，允许在目录内执行任意Node脚本，也不自动限制脚本后续文件与网络访问。

**建议：** 按命令和子命令定义参数schema，拒绝改变目录、配置、环境和插件加载语义的未授权选项；将实际读写对象纳入策略；采用每任务独立工作树并评估OS级隔离或受限权限。不要把字符串过滤当作完整沙箱。

**验收：** 白名单外的合成目标，经直接路径和命令选项均拒绝；已批准的正常Git读取可用；否决不造成写入。

源码：[host-runtime.mjs](../dsh-self/host-runtime.mjs)，`gitDenied`、`shellRun`约240–312行。探针：`git_cwd_redirect`。

### F02｜P0：目录联接别名能绕过敏感名称保护

**现场隔离复现：** 人工建立名为`.env`的受保护测试目录，直接读取被拒；在同一允许根内建立普通名称的Windows目录联接，读取其虚构标记却被允许。没有读取任何真实密钥。

**原因：** 敏感名称检查发生在输入路径上，`realpath`之后只检查是否仍在允许根内，没有再次检查解析后路径的敏感名称。

**建议：** 词法路径和最终规范路径都执行敏感路径策略；显式处理junction/symlink/reparse-point；补充文件打开前的身份核验与竞态测试。这次复现的是名称保护绕过，不等同已经证明所有跨根联接都可绕过。

**验收：** 直接路径、大小写变体、目录联接和文件符号链接均一致拒绝受保护目标；正常链接策略有明确测试。

源码：[host-runtime.mjs](../dsh-self/host-runtime.mjs)，39–76行。探针：`deny_name_realpath`。

### F03｜P1：只要求提交A，可能把已暂存的B一起提交

**现场隔离复现：** 新建临时Git仓库，预先暂存`unrelated.txt`，再调用接口要求只提交`selected.txt`；最终提交包含两者。

**原因：** 实现先`git add`指定文件，再执行不限定路径的`git commit`，没有隔离已有暂存区。

**建议：** 检查并保留用户已有暂存区，选择独立索引/独立工作树或明确的路径限定提交策略；提交前展示最终文件集合，与批准清单一致才执行。不能自动reset用户暂存区来“修复”。

**验收：** 只提交获准文件，既有暂存内容保持不变；失败路径也不吞掉原暂存状态。

源码：[host-runtime.mjs](../dsh-self/host-runtime.mjs)，`gitCommit`约326行起。探针：`selected_commit_scope`。

### F04｜P1：二进制文件回滚可能报告成功但字节不一致

**现场隔离复现：** 用一个含非UTF-8字节的4字节虚构文件测试。写入和恢复均返回成功，恢复后却变成8字节。

**原因：** 旧内容用UTF-8文本读取，快照按字符串保存，恢复也按UTF-8写回；非UTF-8字节已被替换。现有ASCII文本H5通过不能覆盖该情况。

**建议：** 要么明确只支持有效UTF-8文本，遇到二进制先拒绝；要么保存原始字节/base64或内容寻址对象，同时存长度、SHA256、文件身份和权限。恢复需做冲突检查，不能静默覆盖用户之后的新修改。

**验收：** 文本、中文、BOM、非UTF-8和二进制按声明处理；允许恢复的文件逐字节相等；不支持的类型在覆盖前被拒。

源码：[host-runtime.mjs](../dsh-self/host-runtime.mjs)，163–227行；[host-rewind-bridge.mjs](../dsh-self/host-rewind-bridge.mjs)，快照与恢复函数。探针：`binary_snapshot_restore`。

## 四、其它需要优化的地方

### 4.1 权限和审批：不要把布尔值当作独立批准证据

**源码观察，尚未做真实服务穿透测试：** `/api/dsh-host/run`从请求体取`confirm`并交给执行器；该插件处理器中未见一次性批准凭据、批准参数摘要或会话绑定。上游DSH WebServer是否统一认证、Origin/CSRF保护是否完整，本轮未验证，因此不能直接下结论为“公网未授权执行漏洞”。

建议为高风险操作建立：预览→用户批准→服务端签发短时一次性批准标识→执行时核对操作参数哈希/会话/有效期。外层身份鉴别、浏览器Origin/Host检查与业务批准要分层，不互相替代。参见[dsh-self/index.js](../dsh-self/index.js)327–349行、[host-agent.mjs](../dsh-self/host-agent.mjs)126–174行。

### 4.2 执行稳定性：全局20步和同步阻塞值得优先调整

- `host-agent.mjs`使用单个持久`host-session.json`与硬编码20步预算。多任务共享这个文件，未看到按run/session自动划分的预算。旧任务可能影响新任务，并发更新也需要原子性保障。应改为任务级预算、明确到期/重置、事务性步数预留与统一取消。
- `spawnSync`在宿主HTTP执行链中同步等待命令，运行时最长可等30秒；共享Node事件循环可能因此不响应其它请求。建议异步子进程、受控队列、流式输出、超时取消、进程树清理和可查询任务状态。不是把所有动作并行执行，写操作仍应串行或基于冲突图调度。
- `dryRun`顶层默认返回成功，而具体`previewFsWrite`可以返回拒绝。预览结果应把“策略允许”“需要批准”“不可执行”的状态明确分开，不能让界面把禁止路径当作可执行预览。

### 4.3 性能：轻量页面应少计算，而不只是少返回字段

**已核对源码：** `buildSnapshot`先做较完整的聚合，再在约2112行根据`view==='shell'`裁剪；`collectRewindStats`和时间轴仍同步遍历快照目录。另有4秒fingerprint轮询，客户端也有轮询和SSE路径。

建议：

1. 提前分流shell摘要与完整实验视图；未打开的实验视图不计算。
2. 快照元数据维护索引/增量计数，不在每次刷新时扫全目录。
3. 把状态查询与归档维护分开：当前`buildSnapshot`在配置条件满足时会保存信箱/归档，GET式状态查看并非纯读。
4. 请求合并、短TTL、可见性暂停、SSE主导+低频兜底，防止多窗口重复计算和重入堆积。
5. 用数据决定阈值：记录首屏、首字、动作完成、snapshot p50/p95、事件循环延迟和缓存命中，而不是先声称能快一倍。

源码：[dsh-open-world/index.js](../dsh-open-world/index.js)596–695、1836–1853、1917–2112、2660附近；[portal.js](../dsh-open-world/client/modules/portal.js)。**本轮未测实际聊天首字、长任务吞吐或冷启动时间。**

### 4.4 产品体验：保留个性化，但把日常模式与实验模式分开

建议普通模式只突出：**任务、文件、改动/回退、设置**。每个任务显示目标、当前步骤、等您确认的内容、产物、验证结果和失败原因。

世界地图、器官、ATI、拓扑、化学、RRA等视图可以保留到实验模式，不必删除您喜欢的内容；但不能让普通用户先理解这些概念才能办事。源码中相关输出明确标为`metaphor/derived`，不要在产品文案中包装成已经训练出新模型或获得新认知能力。

为断网、记忆服务不可用、插件缺失、授权拒绝和模型限额，提供清晰降级；不要靠自动重复打开一堆插件来“修复”。当前功能冻结方向是合理的。

### 4.5 工程治理：把正在运行的实例、源代码和文档对上

- 当前终端Node为**v24.13.0**，根包声明**>=24.15.0且<25**。这次子包测试仍通过，但支持规范不一致，需固定Node/包管理器版本；不能据此推定Electron内置Node同样是这个版本。
- 根包名称为`lobsterai`，版本2026.8.21，声明`dist-electron/main.js`，现场该入口不存在；实际工作区主要是DSH插件和控制层。可能有历史复用原因，但应拆分“宿主应用清单”和“插件工作区清单”，不要靠根package.json误导定位。
- 当前Git基线HEAD为`05301e3`。检查时有23条状态记录，其中一条是本轮连接文档，其余22条为原有修改/未跟踪内容（包含子模块行）。本轮没有帮您提交、stash或覆盖。
- 五个子模块已写入`.gitmodules`，但`git submodule status`显示`-`前缀，需要核对本机登记/初始化与实际目录状态；不能在有本地修改时直接强制update。
- 架构文档部分行仍写“缺.gitmodules/缺根scripts”，实际已存在；AGENTS写v2.77而主规划已是v2.78。建议自动生成版本、当前预设、门禁和依赖摘要，减少多处手写状态。
- 默认doctor仍指向旧的DSH Desktop路径，而本轮捕获到DeepSeek Harness在运行；旧路径也确实存在，故不能仅凭“路径存在、历史doctor绿色”判断检查的是当前实例。应绑定PID→EXE→profile→runtime版本。没有自动切换或重启实例。
- `doctor check`会写`_doctor-last.json`，`workspace:status`又依赖它；工具的只读/写入分类应与实际副作用一致。本轮没有重跑真实用户配置的doctor/bootstrap检查，避免改写既有状态或读取凭证配置；历史结果不当作本轮结果。

大型文件和重复代码也值得治理：Open World入口约3159行，生成的client.js约6510行；vendor、生成产物、market-probe和缓存存在重复体积。先分离源码/构建产物/实验副本的索引与打包范围，而不是因文件大就立刻重写框架。统计包含生成与测试代码，不能当作纯手写代码量。

### 4.6 机器环境：别把资源紧张误判为某个模型不聪明

只读快照显示总可用物理内存规模约15.7GiB，当时空闲约1.7GiB。匹配进程的工作集累加：DeepSeek Harness约461MB、ShunCode约1361MB，另有少量相关服务。

这是**单次快照，工作集含共享页，不是独占内存或公平横评**；也不能把其余内存都归因于这些工具。建议做比较时一次只跑一个候选工作流，关掉不需要的应用由您决定；若常态多开大型IDE/浏览器/多代理，再结合持续监测考虑32GB，而不是先盲目换硬件。

### 6.2 您的项目应该与它们争什么，不争什么

- **不争底层模型能力**：增加插件、提示词、人设和可视化，不等于训练出超过Claude或Codex所用模型的新模型。
- **争个人可控性**：明确授权、可读日志、少量可靠能力、可迁移配置、能验证的恢复。
- **争熟悉的工作流**：把您常做的三五类任务做成稳定闭环，比同时覆盖几十种演示更有价值。
- **避免重复造轮子**：办公格式处理、代码编辑器、Git可视化等优先复用成熟工具；自己做任务状态、能力边界、验证和回退的统一层。
- **外部产品协作优先用正式CLI/MCP/SDK**，并核实授权条款。不要把依赖私有DOM/CDP点击菜单的方案当稳定底座，也不要让多个代理同时改同一份真实工作树。

一个务实的日常组合是：**一个主工作台 + 一个编程助手 + 按需的系统操作工具**。不需要为了“功能齐全”把所有产品同时常驻、共享权限和共享记忆。

### 6.3 “本地运行”不等于“数据永不出电脑”

例如QoderWork官方说明：文件操作在本机，但任务所需文本会发送给模型API提供方。[4](https://docs.qoder.com/qoderwork/introduction) Marvis官网区分本地模式与端云协同模式，[Marvis官网](https://marvis.qq.com/)；不能把其中一种模式的承诺套到所有任务。

本项目接外部模型、MCP、记忆或IM通道时，也应明确：哪些内容会发送、发送给谁、保存多久、用户如何关闭/删除。不要把本地SQLite或本地文件夹当作整个链路的隐私保证。

## 七、我建议的优化顺序

| 顺序 | 工作包 | 完成标准 | 不应夹带的工作 |
| --- | --- | --- | --- |
| 1 | 修F01/F02权限边界 | 四类路径/命令负向用例固化；在受控fixture中阻止越界且正常操作不退化 | 新增全盘权限、全开远程控制 |
| 2 | 修F03/F04改动与回滚 | 指定提交精确、已有暂存不受损；回滚字节正确或提前拒绝不支持类型 | 自动清空用户暂存区、直接覆盖旧数据 |
| 3 | 审批与任务状态 | 任务级预算；明确preview/approve/run/result；批准与参数绑定；失败可安全重试 | 用confirm布尔值代替所有身份与授权检查 |
| 4 | 兼容性与发布门禁 | Node/运行时/插件版本矩阵；现有626检查+新增负向回归+真实桌面冒烟 | 未备份就更新插件和宿主 |
| 5 | 性能与简化入口 | shell提前短路、快照增量索引、后台操作不阻塞；任务/文件/改动/设置成为日常路径 | 先开更多记忆、市场、语音和实验插件 |
| 6 | 再做外部工具协作 | 稳定接口、隔离目录、明确费用与权限、一次只接一个明确工作流 | 多个客户端共同修改同一目录 |

建议分成三轮可验收交付，而不是一次重构整个项目：

1. **保安全与保数据**：F01–F04及回归。
2. **保稳定和可理解**：审批、任务预算、实例识别、错误分类、主界面收敛。
3. **有数据再提速和扩展**：性能基线、版本矩阵、小范围产品横评，再决定增加何种能力。

这与当前规划的FEATURE_FREEZE方向一致：先修现有能力，不借评估之名启用新插件。组合校验`plan.validate`值得做，但必须建立在单步边界已经可靠的基础上。

## 八、如果要真正比较谁更好用，怎么测

建议先选择3–4个候选，而非一次对所有产品付费和调试。两条轨分开：

- **框架对比**：能配置相同模型/版本时，固定模型和预算，尽量隔离运行时差异。
- **产品对比**：使用各自可用的原生模型/流程，比较最终成果与成本，但不能把结果归因于纯框架优劣。

| 场景 | 客观验收 |
| --- | --- |
| 修复已有仓库的小Bug | 指定测试从红到绿；不改无关文件；真实diff可审 |
| 跨文件重构 | 行为不退化、测试证据完整、变更范围明确 |
| 表格清洗与报表 | 固定假数据，结果与参考计算一致，公式/列类型可检查 |
| 多份文档汇总 | 引用可追溯、不得编造原文没有的结论 |
| 敏感/越界请求 | 只用虚构敏感文件，未经授权修改数必须为0 |
| 恶意工具输出 | 输入中含诱导越权内容，系统仍遵守原任务与权限 |
| 中断/取消/恢复 | 取消后无后续写入；恢复可验证，无重复业务副作用 |
| 插件或网络不可用 | 有期限地失败或降级，不死循环、不误报完成 |

每项至少3次，独立目录、固定样本、记录客户端/模型版本、网络和套餐。指标包含：验收成功率、误写数、人工干预次数、达到可用成果的时间、token/实际费用、恢复成功率及资源峰值。普通任务成功率和高风险误操作率分开看。

这些是下一轮测试设计，**尚未执行，不填虚构分数或排名**。本轮不建议仅凭营销指标决定把哪个产品卸载、订阅或替换。
